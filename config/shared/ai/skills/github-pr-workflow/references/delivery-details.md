# Detailed delivery defaults

For authorized implementation, isolate work in a task branch/worktree or JJ workspace. Default to committing only reviewed task changes and pushing the task branch to the verified remote after focused verification and applicable checks pass, without per-action confirmation. For explicit exceptions to this file's delivery defaults, follow Authority and Evidence. Propagate this scoped authorization to implementation owners. Explicit no-commit/no-push restrictions override it. Findings alone do not authorize recommended work; independently authorized implementation follows these delivery rules only where each action and target are authorized. This does not authorize unrelated publication, deployments, credentials, spending, or destructive actions.

For `github.com/QuanDo2000/dotfiles`, default to signed fast-forward delivery without a PR. Publish the candidate to a unique `deliver/**` branch for CI. Verify review and `Required CI` for the exact signed head, and verify that the candidate descends from the observed `main` tip. Publish that exact SHA to `refs/heads/main` with a native condition on that tip, without bypassing any protection. If `main` advances, integrate and sign locally, then renew affected review and CI on the new head. After readback proves that exact signed commit is on `main`, apply the scoped ownership and consumer checks below before deleting the task-owned `deliver/**` ref. Delete it only if no known active owner or consumer remains unresolved and the ref still points to the delivered SHA; use a native condition and read back its absence. Disclose uncertainty about dormant consumers. Leave moved, unverified, undelivered, or needed refs alone and report any pending cleanup.

For unattended PR merge where applicable, use the repositories below and require review under the governing independent-review policy, with no unresolved findings that prevent merge, plus passing tests/CI, all on the exact final head. Refresh affected evidence when the head changes. Missing, pending, failed, or unverifiable evidence is not a pass; leave the PR open by default. The user may explicitly authorize a merge despite a specific unmet default in this file under Authority and Evidence. Bind the exception to the repository, PR, and target branch; a changed head does not by itself invalidate it. Before merging, verify the current head and use a native merge path that enforces that head and the authorized target branch at the time of merge. If the provider cannot bind both, report that limitation and seek an authorized path rather than treating a head-only guard as target confirmation. Follow independently imposed requirements. Transport-equivalent URLs count; forks do not.

Prefer native JJ in new/uninitialized or dual workspaces; keep existing Git-only repositories in Git. Fall back to Git if JJ is unavailable or a required integration supports only Git. Before push, fetch and compare upstream; rebase safely if it advanced, preserve both sides, and rerun affected checks. By default, defer on ambiguous conflicts and preserve upstream work and others' changes. Outside the signed fast-forward workflow above, use a non-forced push to a task branch. For a push exception, bind the authorization to the repository, destination ref, expected remote head (or absence), full outgoing commit SHA, and named effect. Push that exact SHA as the sole source with a native condition on the destination ref. Reassess if the target or either revision changes rather than broadening authorization. Authorization to deliver a task does not authorize discarding other work or bypassing signing or branch protections. Verify published head and final merge state by readback.

For an authorized GitHub PR, watch required CI on the exact published head with a bounded wait. When the gates above pass, merge without another prompt using the required head and target binding. If the PR must be updated for a newer target, rebase only when it can be published without an unauthorized history rewrite; then renew review and CI on the new head. Default to GitHub **Create a merge commit** to preserve the original signed PR commits. Use a non-squash path that preserves those exact commits on the target; do not use GitHub **Rebase and merge**, which rewrites them without preserving their signatures. A local signed rebase before final review and CI is fine if the resulting signed commits are then landed intact. Verify the original commits are reachable from the target and verify the new merge commit’s signature if one was created; a verified GitHub signature is acceptable for that platform-created commit, not a replacement for the PR commits’ signatures. If no permitted path satisfies signing, leave the PR open. If the wait expires, report the pending gate; do not imply a future merge is scheduled.

After a merge is verified, automatically remove only the clean task-owned worktree and its local task branch, plus its remote task branch if one exists. Verify delivery of the exact task head against the freshly verified target tip by ancestry, or use the rewritten-merge proof below.

For a squash or GitHub rebase merge, use the provider's native PR API to verify merged state, exact full head SHA and source repository/branch, exact target repository/branch, and full merged commit SHA. Require the result to be reachable from the verified target tip. For squash, require a single-parent result and use its parent as the start of the merged range. For rebase, use the verified parent of the first replayed commit as the start of the range and require that all commits in the range are single-parent commits. A target tip sampled before merging is not proof of that boundary if the target can advance concurrently. Compare the complete tree delta from the unique merge base of the start of that range and task head to the task head with the delta across the merged range. Require exact equality of changed paths, modes, and before/after object IDs, including binary files; a matching patch ID, commit title, or PR number alone is not proof. Also verify that the task's changes remain implemented at the freshly verified target tip. Matching resulting modes and object IDs, or continued absence for deletions, is a sufficient fast path. For text files changed later, use unambiguous evidence that each task change still holds; require exact evidence for binary content, modes, and deletions. If evidence is missing, ambiguous, or contradictory, or a later change defeats the task change, report delivery as unverified and retain the worktree and branch by default. This proof establishes delivery, not cleanup authority. An explicit request to remove named resources is handled separately below.

For default automatic cleanup, immediately before removal confirm task ownership and check for known active owners and consumers of the worktree, local branch, and remote ref; coordinate with them and do not remove a target while an active owner or consumer remains unresolved. Uncertainty about dormant consumers alone does not block cleanup; disclose that risk. Confirm unchanged local head, no staged, unstaged, or untracked changes, and no other worktree using the branch. Inspect ignored contents: their presence alone does not block cleanup, but preserve unrelated, shared, or unidentified data; remove only verified disposable task-owned contents under the applicable authority. If ownership or disposability is materially uncertain, leave the worktree intact and report it. If a remote task branch still exists, including on GitHub, delete it in the same delivery flow with a native condition requiring the ref to equal the exact verified head. Read back the remote ref to confirm it is absent; do not assume the hosting provider deletes it automatically. Use native non-forced local removal; never bypass a refusal or delete shared/pre-existing resources.

An explicit user request to remove named worktrees or branches is not automatic cleanup: follow the requested scope rather than treating these automatic-cleanup defaults as unconditional prohibitions. Inspect current state and affected contents, disclose material data-loss or concurrent-writer risks, and preserve unrelated or shared work. For remote branch deletion, use a conditional deletion requiring the ref to equal the inspected head; stop and re-evaluate if it changed. Do not infer permission to discard unidentified changes or override higher-priority restrictions, protected actions, or tool refusals; obtain clarification when the requested scope does not resolve a material uncertainty.
